# Security-ревью и «дыры» в разработке

Дата: 2026-06-25. Метод: ручной аудит кода (auth, JWT, OTP, загрузка файлов,
чат/WebSocket, RBAC, логирование, конфиг). Найдено: 3 критических, 6 высоких,
5 средних, несколько низких. Ниже — с местом в коде, воздействием и фиксом.

Легенда: 🔴 критично · 🟠 высоко · 🟡 средне · ⚪ низко.

---

## 🔴 Критические

### S1. OTP-код пишется в лог
`app/services/otp.py:117` — `send_sms()` логирует и телефон, и **сам код**:
`logger.info("sms_otp_sent", {"phone": phone, "code": code})`.
Любой, у кого доступ к логам, может входить в любые аккаунты; плюс это ПДн (152-ФЗ).
→ Не логировать код никогда. В dev — максимум маскированный телефон; в prod —
отправлять через провайдера без логирования тела.

### S2. Дефолтный JWT-секрет без защиты
`app/core/config.py` — `jwt_secret: str = "change-me-in-prod"`, без проверки на
старте. Если задеплоить без override — секрет известен, **токены подделываются**
(полный обход аутентификации, вход под любым `user_id`).
→ На старте падать, если `environment=prod` и секрет дефолтный/короткий; секрет
из переменной окружения/секрет-менеджера.

### S3. ПДн (телефон) хранятся в открытом виде
`app/models/user.py` — `phone` без шифрования; `debug=True` по умолчанию включает
`echo=True` у движка (`app/db/session.py`), т.е. SQL с ПДн льётся в логи.
→ Шифровать PII в покое (KMS), `debug=False`/`echo=False` в prod, чистить логи.

## 🟠 Высокие

### S4. Блокировка не прекращает контакт (обход блокировки)
Блокировки учитываются только в ленте подбора (`services/discovery.py::_excluded_ids`),
но **не проверяются**:
- при лайке — `app/api/v1/routes/discovery.py` (`like`/`_record` не смотрят `blocks`);
- при отправке сообщения — `app/api/v1/routes/chat.py:96` (`send_message` проверяет
  только членство в мэтче);
- при инициации видеозвонка — `app/api/v1/routes/video.py`.
Итог: заблокированный пользователь может образовать мэтч и **продолжать писать/звонить**.
Для дейтинга это прямая угроза безопасности пользователя.
→ Централизованная проверка «есть блок в любую сторону» в like/message/video.

### S5. Телефон (ПДн) в аналитике/логах
`app/api/v1/routes/auth.py:50` — `track_event("otp_requested", {"phone": phone})`,
а `services/analytics.py` пишет свойства в лог. Телефон утекает в логи/аналитику.
→ Хэшировать/не передавать телефон; в аналитику — обезличенный идентификатор.

### S6. Нет отзыва/ротации refresh-токенов и logout
`app/api/v1/routes/auth.py:117` — `refresh` выдаёт новую пару без инвалидции старой;
logout отсутствует; JWT stateless. Утёкший refresh даёт доступ до 30 дней.
→ Ротация с денилистом (Redis) или `token_version` на пользователе; `/auth/logout`.

### S7. SMS-pumping / toll fraud
`request-otp` лимитирует **только по телефону** (5/час), нет лимита по IP/устройству.
Злоумышленник рассылает OTP на тысячи номеров → расходы на SMS и абуз.
→ Лимит по IP + captcha/app-attestation при аномалиях; глобальный rate-limit.

### S8. Загруженные фото не отдаются + отсутствует валидация содержимого
Статика `media_base_url=/media` не смонтирована (`app/main.py`) — URL фото не
резолвится (**функционально не работает**). При будущем монтировании: нет проверки
magic-bytes, недопустимое расширение молча заменяется на `.jpg`
(`services/storage.py:20`) — риск хранить не-изображение; раздача с того же origin —
потенциальный stored-XSS.
→ Раздавать медиа с отдельного домена/CDN, валидировать сигнатуру файла,
`Content-Disposition`, отклонять недопустимые типы явно.

### S9. PII-шифрование и хранение в РФ — не реализовано
Требование 152-ФЗ: хранение и шифрование ПДн. Сейчас — открытое хранение,
интеграции-заглушки. (Дублирует S3, вынесено как комплаенс-риск.)

## 🟡 Средние

### S10. Слабый OTP и DoS легитимного пользователя
4-значный код (`otp_length=4`). `verify-otp` инкрементит счётчик попыток **до**
проверки и при превышении **удаляет код жертвы** (`auth.py:61-75`) — атакующий,
зная номер, может блокировать вход жертвы, спамя неверные коды.
→ 6-значный код; счётчик попыток привязывать к конкретному коду; не удалять код
жертвы из-за чужих попыток; лимит по IP.

### S11. Нет CORS-политики
`app/main.py` — CORS не настроен. Веб-клиент не заработает; при последующей
настройке важно **не** ставить `allow_origins=["*"]` вместе с credentials.
→ Явный whitelist origin для web.

### S12. Нет глобального rate-limit и антифрод синхронный
Кроме OTP, лимитов нет; `evaluate_and_apply` крутится в `send_message` синхронно.
→ Глобальный rate-limit (reverse-proxy/middleware), антифрод — в фон.

### S13. «Висящие» видеосессии
`video.py` — сессия `requested`/`active` не имеет серверного TTL; можно накапливать.
→ Авто-истечение по таймауту, серверный лимит длительности.

### S14. Повторное согласие при смене версии документа не запрашивается
Обязательные согласия проверяются только при регистрации (`auth.py`); при росте
версии документа существующие пользователи не переподтверждают (152-ФЗ).
→ Middleware, требующий согласие при устаревшей версии.

## ⚪ Низкие / hardening
- Лайк произвольного `user_id` без проверки существования/видимости цели — позволяет
  зондировать наличие взаимного лайка. → Проверять, что цель в допустимой выборке.
- `register_device` переназначает чужой токен на нового пользователя (`notifications`)
  — потенциальная путаница push. → Привязку токена подтверждать.
- Нет security-заголовков (HSTS, X-Content-Type-Options, CSP) — уровень reverse-proxy.
- Нет проверки размера WebSocket-сообщений/частоты (`chat_ws`). → Лимиты на WS.

## Что именно «не работает» (баги)
1. **Фото не отображаются** — статика не смонтирована (S8).
2. **Гео-подбор не работает** — координаты не используются в фильтре (см. audit F2).
3. **Блокировка не защищает** — заблокированный продолжает контакт (S4).
4. **Логин можно заддосить** — чужие попытки удаляют OTP жертвы (S10).

## Итог
Архитектура и разграничение доступа (RBAC, проверки членства в мэтче/владения фото,
пиннинг JWT-алгоритма) — на хорошем уровне. Но есть **критические** утечки секретов
в логи, риск дефолтного JWT-секрета и **обход блокировки** — их надо закрыть до
любого публичного запуска. Path-traversal/SQL-инъекций не обнаружено (ORM +
UUID-имена файлов).

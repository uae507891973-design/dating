сценариев, сверка с планом ([development-plan.md](./development-plan.md)) и

## 1. Функциональные находки

Серьёзность: 🔴 высокая · 🟡 средняя · ⚪ низкая.

### 🔴 F1. Загруженные фото не отдаются
`media_base_url=/media`, файлы пишутся локально (`services/storage.py`), но в
приложении **нет монтирования статики** (`StaticFiles`) и нет CDN — URL фото в
ответах (`/media/...`) не резолвится. Подбор/анкеты визуально пусты.
→ Смонтировать статику для dev и подключить объектное хранилище РФ для прод.

### 🔴 F2. Гео-подбор не реализован
`latitude/longitude` сохраняются, но в `services/discovery.py` **не используются**:
нет фильтра по радиусу и по городу. Заявленная гео-функция отсутствует.
→ Добавить фильтр по городу/радиусу (PostGIS на проде), параметр `max_distance_km`.

### 🟡 F3. N+1 в подборе
`get_candidates` вызывает `load_answers` **в цикле по каждому кандидату**. Фото и
верификация уже берутся батчами, а ответы — нет. На масштабе — деградация.
→ Один запрос ответов по всем кандидатам + кэш кандидатов в Redis.

### 🟡 F4. Нет отзыва токенов / выхода
JWT stateless, refresh не ротируется и не инвалидируется, эндпоинта logout нет.
При утечке refresh — доступ до истечения 30 дней.
→ Ротация refresh, денилист (Redis) или `token_version` на пользователе; `/auth/logout`.

### 🟡 F5. Нет гейта заполнения анкеты перед подбором
Пользователь без `gender/looking_for` получит некорректную/пустую выдачу. Онбординг-
тест создаёт профиль только с `intent`. Нет проверки «профиль заполнен».
→ Гейт «заполните анкету и фото» до доступа к подбору; флаг полноты профиля.

### 🟡 F6. В ленту попадают не прошедшие тест
Кандидаты без ответов получают `score=0`, но всё равно показываются.
→ Фильтровать кандидатов без психопрофиля (или понижать в ранжировании явно).

### ⚪ F7. Email-флоу не завершён
В модели есть `email`/`password_hash`, но вход только по телефону; пароль не используется.
→ Либо реализовать email-вход, либо убрать поля до востребования.

### ⚪ F8. Нет rate-limit на лайки/сообщения
Антифрод реагирует постфактум; явных лимитов действий нет.
→ Лимиты per-user/min на лайки и сообщения.

### ⚪ F9. Антифрод синхронен на каждое сообщение
`evaluate_and_apply` выполняется в `send_message`, добавляя задержку к отправке.
→ Вынести в фон (очередь/таска), оценивать пачками.

### ⚪ F10. «Висящие» видеосессии
Сессия `requested` не имеет авто-истечения на сервере (таймер только в UI).
→ TTL/авто-`declined` по таймауту; серверный лимит длительности `active`.

### ⚪ F11. Нет повторного согласия при смене версии документа
Обязательные согласия проверяются только при регистрации; для существующих
пользователей при росте версии документа повторное согласие не запрашивается.
→ Middleware: при устаревшей версии — требовать переподтверждение.

## 2. Юзабилити-находки

### 🟡 U1. Долгий time-to-value
После регистрации — сразу обязательный тест (16 вопросов) до первой ценности
(подбора). Риск отвала на онбординге.
→ Показать 1–2 карточки/«превью» до теста, прогресс-бар с возможностью «заполнить позже», сократить обязательный минимум вопросов.

### 🟡 U2. Верификация не предлагается в потоке
Раньше бейдж «Verified» висел всегда; теперь (исправлено) появляется только после
регистрации, а в профиле есть действие верификации. В проде стоит показывать мягкий
промпт верификации сразу после онбординга (повышает доверие и качество ленты).

### 🟡 U3. Нет «пустого состояния» подбора
Когда кандидаты заканчиваются — нужен экран «на сегодня всё», предложить расширить
фильтры/радиус. (В прототипе лента зациклена на демо-данных.)

### ⚪ U4. Юр-документы не открываются
Ссылки на «Согласие…»/«Оферту» — заглушки. Нужен экран/страница с текстом документа
(особенно важно для 152-ФЗ и доверия).

### ⚪ U5. Доступность (a11y)
Кнопки-эмодзи (лайк/скип/видео) имеют `title`, но без `aria-label`; контраст
некоторых muted-текстов на грани. → Добавить `aria-label`, проверить контраст.

### ⚪ U6. Чат: нет индикаторов «печатает»/прочитано в UI
В API статус `read` есть, в интерфейсе не отражён; автоответ — заглушка.
→ Показать статусы доставки/прочтения и индикатор набора.

### ⚪ U7. Нет онбординг-подсказок по безопасности свидания
Бренд про безопасность — стоит добавить ненавязчивые советы перед первой встречей.

## 3. Безопасность и комплаенс
Прикладной контур (согласия с версионированием, OTP с лимитами, RBAC, модерация
фото, верификация, антифрод, аудит, антиспам в чате) — реализован. Открыто:
шифрование PII в покое, реальный SMS/push/RTC, хранение ПДн в РФ, тексты документов.
Детали — [security-152fz.md](../security/security-152fz.md).

## 4. Производительность
Узкие места: N+1 в подборе (F3), синхронный антифрод (F9), отсутствие кэша
кандидатов и курсорной пагинации в ленте. На бете при росте аудитории — приоритет P1.

## 5. Приоритизированный план

### P0 — до открытой беты
- F1: раздача фото (StaticFiles в dev + объектное хранилище).
- F5/F6: гейт заполнения анкеты + фильтр прошедших тест.
- F2: хотя бы фильтр по городу в подборе.
- U2: промпт верификации после онбординга.

### P1 — стабилизация
- F3: устранить N+1 + кэш кандидатов (Redis).
- F4: ротация/отзыв refresh + logout.
- F9: фоновый антифрод.
- U1: ускорить time-to-value; U4: экраны юр-документов.

### P2 — улучшения
- F7 (email), F8 (rate-limit), F10 (TTL видео), F11 (reconsent).
- U5 (a11y), U6 (статусы/печатает), U7 (советы по безопасности).

## 6. Вывод
Продукт функционально дошёл до конца Стадии 3 и держит заявленные дифференциаторы
(объяснимый мэтчинг, видео «вслепую», доверие/антифрод). Для открытой беты
критично закрыть 4 пункта P0 (в первую очередь раздачу фото и гейты анкеты/теста).
Остальное — управляемый бэклог P1/P2 в рамках Стадий 4–5.
